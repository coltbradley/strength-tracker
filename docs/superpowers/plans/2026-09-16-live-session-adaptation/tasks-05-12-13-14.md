The RLS insert policy (`with check (user_id = auth.uid())`) is unaffected because the payload leaves `user_id` to its column default, same as every other outbox insert.
- `lib/sync.ts`'s `transport.insert` is generic (`.from(table).upsert(payload, { onConflict: keyed ? **What the real mechanism turned out to be (read `Today.tsx`/`End.tsx` in full before starting — this replaces the spec's "bump doneTick" framing):**

`doneIds`/`doneTick` is a red herring. `Today` and `End` are different routes
under the same `<Routes>` in `App.tsx`, so navigating `/end` → `/` always
unmounts `End` and mounts a **brand new** `Today` instance. Its
`getDoneWorkoutIds` effect (`Today.tsx:525-533`) runs on that fresh mount
regardless of `doneTick`'s value — dependencies don't have to _change_ to run
an effect on initial mount.

The real bug is a race: `getDoneWorkoutIds` goes through `fetchWithCache`,
which is **online-first** (`data.ts:140-163`) — it always calls the server
before ever consulting the cache. `End.tsx`'s `end()` calls
`outbox.enqueue(...)` for the session's `ended_at` patch, but `enqueue()`
itself only _fires_ a flush (`void flush()`, not awaited,
`outbox.ts:536-541`) before resolving. By the time `end()` calls
`navigate("/")`, the network write may not have reached the server yet — so
Today's fresh, online-first `getDoneWorkoutIds` call can win the race and
come back "not done" for a session that just ended.

`markPlannedDayDone` (`End.tsx:238-246`) already exists and already
optimistically patches the _cached_ done-workout list — but that cache
write is exactly what the online-first race clobbers when the read succeeds.
It's not useless: it's what makes the **offline** case correct (`data.ts`'s
`fetchWithCache` falls back to cache on a failed fetch), which is why it
stays.

The fix is a bounded wait on `outbox.flush()` (1.5 s, via `Promise.race`) in `end()`, in the same place
`History.tsx`'s `voidPastSet`/`discardSession` already do this for the exact
same reason ("wait for the queue to be walked so the write is on the server
before we ask the server what is live"). This makes the online case correct
without inventing any new event bus, and needs no change to `doneTick` at
all.

**On "sets, working volume and duration" — scope cut, flagged:**

`working volume` (tonnage) is deliberately **not** implemented here. Per
CLAUDE.md, derived metrics like this live in SQL views only
(`v_weekly_volume` already computes it, with the correct `tracking`/`set_type`/
`load_entry` filtering) — reimplementing that arithmetic ad hoc in `End.tsx`
would create a second, driftable definition of "working volume" outside the
one file scope for this task allows touching (no new SQL view, no new
`lib/data.ts` export is in this task's file list). `sets` (a plain count,
already computed and shown on the End screen itself) and `duration` (plain
`ended_at - started_at` arithmetic, already computed and formatted by
`formatDuration`, also already on the End screen) are **not** that kind of
derived metric — they're the same numbers End already displays, just handed
forward. If a future task wants working volume on the DONE card, it should
add a real per-session read against `v_weekly_volume`'s equivalent
filtering, not extend the raw cache key introduced here.

## Summary of contract deviations (all four tasks)

1. **Task 5 — no `feedback` migration.** `feedback.id`'s
   `default gen_random_uuid()` only applies when the column is omitted from
   an insert; a client-supplied UUID overrides it, same as every other
   outbox table. Verified by reading the migration SQL and RLS policy
   directly; no `20260917040000_feedback.sql` is created.
2. **Task 5 — `lib/sync.ts` and `components/ReportBugSheet.tsx` need no
   code changes**, despite being in the build plan's file list for this
   task. `sync.ts`'s `transport.insert` is already generic over the table
   name; `ReportBugSheet.tsx`'s contract with `sendBugReport` is unchanged.
3. **Task 5 — verified, not just reasoned about, that `errors.ts` importing
   `sync.ts` (which cycles back to `errors.ts` through `checkinMemory.ts`)
   is safe** by making the change directly in the worktree, running
   `npm run build` and the `PrimaryNav` test suite, then reverting — see the
   verification note under Task 5.
4. **Task 12 — the spec's "bump doneTick" framing is not the real fix.**
   Today remounts fresh on every navigation to `/`, so its `doneIds` effect
   already runs on mount regardless of `doneTick`. The actual bug is
   `fetchWithCache`'s online-first read racing `enqueue()`'s un-awaited
   fire-and-forget flush; the fix is a bounded `outbox.flush()` wait (1.5 s) in `end()`,
   mirroring the identical pattern already used in `History.tsx`.
5. **Task 12 — "working volume" is explicitly out of scope**, to avoid a
   second, driftable, ad hoc definition of a number `v_weekly_volume`
   already owns correctly. Only set count and duration — both already
   computed on the End screen — are carried forward.
6. **Task 13 — `App.tsx` needs no change.** The topbar is already one
   grouped cluster in the DOM; the "two menus" read was caused by a single
   CSS override (`.header-action-coach`) giving the coach icon full ink
   while its neighbours were already dim. Removing that one rule is the
   entire fix.
7. **Task 14 — `BodyweightRow` and its outbox write already exist**
   (shipped in PR 2, commit `085dc7e`), currently on Today only. This task
   adds the same, unmodified component to History rather than rebuilding
   its read/write logic a second time, and leaves Today's copy untouched.

No feedback migration is needed for Task 5.
